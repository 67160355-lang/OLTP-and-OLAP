## 1. OLTP

### โค้ดที่แก้ (`oltp_demo.py`)

```python
cur = con.execute(
    "UPDATE orders SET status='PAID' WHERE order_id='O1004' AND status='PENDING'"
)
print('rowcount:', cur.rowcount)
con.commit()
```

### ผลรันสองรอบ

| รอบ | Before | rowcount | After |
|---|---|---:|---|
| 1 | `('O1004','PENDING')` | **1** | `('O1004','PAID')` |
| 2 | `('O1004','PAID')` | **0** | `('O1004','PAID')` |

### คำอธิบาย

- รอบแรกแถวเปลี่ยนได้ เพราะสถานะปัจจุบันตรงเงื่อนไข `status='PENDING'` ในตอนนั้น
- รอบสอง `status` ถูกเปลี่ยนเป็น `PAID` ไปแล้ว จึงไม่มีแถวใดตรงเงื่อนไขทั้งสองอีก ผลคือ `rowcount = 0` โดยไม่เกิด error — นี่คือคุณสมบัติ **idempotent** ของ `UPDATE` ที่มีเงื่อนไขคุม
- ต้องตรวจ `status` ควบคู่กับ `order_id` เพื่อป้องกันไม่ให้สั่งเปลี่ยนสถานะซ้ำ เช่น เปลี่ยนออเดอร์ที่ถูกยกเลิกแล้วกลับไปเป็น `PAID` โดยไม่ตั้งใจ เงื่อนไขทำหน้าที่เป็น "guard" ของ transaction
- กิจกรรมนี้ยังถือเป็น **OLTP** แม้จะมี `SELECT` เพราะ `SELECT` ที่ใช้เป็นเพียงการอ่านสถานะปัจจุบันของหนึ่งเรคคอร์ดเพื่อสนับสนุนการทำธุรกรรม ไม่ใช่การอ่านเพื่อวิเคราะห์หรือสรุปยอดจำนวนมากแบบ OLAP ลักษณะงานคืออ่าน-เขียนทีละแถวและมีความถี่สูง ซึ่งสอดคล้องกับงานประมวลผลรายการ (transaction processing)
- การแก้ `oltp.db` **ไม่ทำให้ `warehouse.db` เปลี่ยนทันที** เพราะเป็นคนละไฟล์ฐานข้อมูลและไม่ได้เชื่อมกันอัตโนมัติ ตามที่ README ระบุว่า `oltp.db` "ไม่ได้ทำ ETL อัตโนมัติ"
- ระบบจริงควรใช้กระบวนการ **ETL/ELT** เป็นรอบ (batch) หรือ **CDC (Change Data Capture)** แบบใกล้เรียลไทม์ เพื่อดึงข้อมูลสถานะจากระบบ OLTP ไปปรับปรุงคลังข้อมูล (data warehouse) อย่างมีการควบคุมและตรวจสอบคุณภาพข้อมูล

## 2. Grain และ Star Schema

### Star Schema

```text
        dim_date
            |
dim_product—fact_sales—dim_store
```

### โครงสร้างตารางและความสัมพันธ์

- **PK:** `fact_sales (order_id, line_no)` — composite key
- **FK:** `date_key → dim_date`, `product_key → dim_product`, `store_key → dim_store`
- **Relationship:** 1:N จาก `dim_date`, `dim_product`, `dim_store` ไปยัง `fact_sales`

```text
+-------------------+
|     dim_date      |
+-------------------+
| PK: date_key      |
|     year          |
|     month         |
|     full_date     |
+---------+---------+
          | 1
          |
          | N
+-------------------+     +-------------------+     +-------------------+
|    dim_product    |     |    fact_sales     |     |     dim_store      |
+-------------------+     +-------------------+     +-------------------+
| PK: product_key   | 1 N | PK: order_id,     | N 1 | PK: store_key     |
|     product_name  +-----+     line_no        +-----+     store_name     |
|     category      |     | FK: date_key      |     |     province       |
|     unit_price    |     | FK: product_key   |     |     region         |
+-------------------+     | FK: store_key     |     +-------------------+
                          |     quantity       |
                          |     amount         |
                          +-------------------+
```

### Grain

**Grain:** 1 แถวใน `fact_sales` คือ **1 บรรทัดสินค้า 1 รายการ ภายใน 1 ออเดอร์ (order line)**

ตัวอย่างเช่น `O1001` มี 2 แถว เพราะซื้อ Tea และ Cookie ในออเดอร์เดียวกัน ดังนั้นไม่ใช่ "1 ออเดอร์ = 1 แถว"

### Dimensions และ Measures

**Dimensions (3):**
1. `dim_date`
2. `dim_product`
3. `dim_store`

**Measures (2):**
1. `quantity` — จำนวนชิ้น
2. `amount` — ยอดขาย = `quantity × unit_price`

### Hierarchy

- **เวลา:** `year → month → full_date`
- **สถานที่:** `region → province → store_name`

### ทำไม `unit_price` ไม่ควรบวกเป็นยอดขาย

`unit_price` เป็น "ราคาต่อหน่วย" (rate) ไม่ใช่ยอดรวม การนำราคาต่อชิ้นจากหลายแถวมาบวกกันจะได้ตัวเลขที่ไม่มีความหมายทางธุรกิจ เพราะยังไม่ได้คำนึงถึงจำนวนสินค้า

ต้องคำนวณก่อนว่า:

```text
amount = quantity × unit_price
```

จากนั้นจึงนำ `amount` มารวมด้วย `SUM()` ได้ เพราะ `amount` เป็นยอดขายที่สามารถบวกได้ (additive) ในทุกมิติ

### ผล q01.sql

| line_count | order_count | units | revenue |
|---:|---:|---:|---:|
| 8 | 6 | 23 | 1390 |

ผลตรงกับข้อมูลใน `warehouse.csv` และข้อมูลในสไลด์ที่ระบุว่ามี 8 รายการ, 6 ออเดอร์ และยอดขายรวม 1,390 บาท

## 3. OLAP

| ไฟล์ | ผลลัพธ์ | Operation |
|---|---|---|
| q02 | 2026-08: 490, 2026-09: 900 | Roll-up (รายเดือน) |
| q03 | Bangkok/Chonburi × เดือน (4 แถว) | Roll-up หลายมิติ (เดือน + จังหวัด) |
| q04 | 09-09: 360, 09-10: 300, 09-11: 240 | Drill-down (เดือน → วัน) |

### WHERE vs HAVING

- `WHERE` ใช้กรองแถวดิบ **ก่อน** การจัดกลุ่ม เช่น กรองเฉพาะเดือนกันยายน
- `HAVING` ใช้กรองผลลัพธ์ **หลัง** `GROUP BY` แล้ว เช่น เลือกเฉพาะจังหวัดที่มียอดรวมมากกว่า 400 บาท

ดังนั้น q07 ต้องกรองเดือนด้วย `WHERE` และกรองยอดรวมมากกว่า 400 ด้วย `HAVING`

### คำตอบคำถามระหว่างทำ

**ก.** q03 เพิ่ม "จังหวัด" ทำให้สามารถเปรียบเทียบยอดขายข้ามพื้นที่ในแต่ละเดือนได้ ส่วน q04 เพิ่มรายละเอียด "วัน" ภายในเดือนกันยายน ทำให้เห็นแนวโน้มรายวัน

- q03 = มิติสถานที่ (เปรียบเทียบเชิงพื้นที่)
- q04 = มิติเวลา (เปรียบเทียบเชิงแนวโน้ม)

**ข.** กรองเดือนด้วย `WHERE` เพราะเป็นเงื่อนไขระดับแถว และกรองยอดรวมด้วย `HAVING` เพราะเป็นเงื่อนไขหลังการ `SUM()`

**ค.** ผลรวมของ q12 คือ:

```text
300 + 240 = 540
```

ซึ่งเท่ากับ Bangkok × 2026-09 ใน q03 คือ **540 บาท** ดังนั้นผลลัพธ์ตรงกัน

### จุดตรวจความถูกต้อง


| category | Bangkok | Chonburi |
|---|---:|---:|

### Assert

ตรวจสอบว่า Total ใน Pivot เท่ากับยอดรวมจากข้อมูลจริง:

```python
p1.loc['Total', 'Total'] == df['amount'].sum()
```

ผล:

```text
1390 == 1390
```

ดังนั้น **ผ่านการตรวจสอบ**

> หมายเหตุ: ควรเลือกตรวจเฉพาะเซลล์ `Total × Total` ไม่ใช่นำทุกเซลล์ที่มีคำว่า Total มาบวกซ้ำกัน

### ทดลอง Excel / Drink Filter

เมื่อตั้ง Filter เป็น `Drink` ยอดรวมจะเท่ากับ **750 บาท**

เนื่องจาก Tea มี 4 รายการ:

```text
100 + 150 + 200 + 300 = 750
```

แกน Pivot:

- **Rows:** province
- **Columns:** month
- **Values:** amount (Sum)

| province | 2026-08 | 2026-09 |
|---|---:|---:|
| Bangkok | 150 | 300 |
| Chonburi | 100 | 200 |

### ทดลอง Error: ลบ `aggfunc`

เมื่อไม่ระบุ `aggfunc` ใน `pivot_table()` pandas จะใช้ค่า default คือ **mean** ไม่ใช่ `sum`

ตัวอย่าง Bangkok เดือนกันยายน มี 2 แถว:

```text
O1005 = 300
O1006 = 240
```

ถ้าใช้ค่าเฉลี่ย:

```text
(300 + 240) / 2 = 270
```

ค่า **270 บาท** จึงหมายถึง "ค่าเฉลี่ยต่อรายการ" ไม่ใช่ยอดขายรวม

หากแก้กลับเป็น:

```python
aggfunc='sum'
```

จะได้:

```text
300 + 240 = 540
```

ซึ่งเป็นยอดขายรวมที่ถูกต้อง

### ความแตกต่างระหว่าง `sum` และ `mean`

| Aggregate | ความหมาย | การใช้งาน |
|---|---|---|
| `sum` | ผลรวมของทุกแถวในกลุ่ม | ใช้หายอดขายรวม |
| `mean` | ค่าเฉลี่ยต่อแถว | ใช้ดูขนาดเฉลี่ยต่อรายการ |

ดังนั้น `sum` และ `mean` มีความหมายต่างกันและไม่สามารถนำมาใช้แทนกันได้

## 5. ตรวจความถูกต้อง

### q09 — UNION ALL

| month | revenue |
|---|---:|
| 2026-08 | 490 |
| 2026-09 | 900 |
| ALL | 1390 |

หากนำทุกแถวที่ได้มาบวกกัน:

```text
490 + 900 + 1390 = 2780
```

จะเกิด **การนับยอดซ้ำ (double counting)** เพราะแถว `ALL` เป็นผลรวมของอีกสองแถวอยู่แล้ว

ดังนั้นต้องเลือกใช้อย่างใดอย่างหนึ่ง:

- รายเดือน (`2026-08`, `2026-09`)
- หรือยอดรวม (`ALL`)

ไม่ควรนำทั้งหมดมารวมกันอีกครั้ง

### q10 — AOV และ Average Line

| revenue | orders | aov | avg_line |
|---:|---:|---:|---:|
| 1390 | 6 | 231.67 | 173.75 |

### หน่วยของ AOV

**AOV (Average Order Value)** มีหน่วยเป็น **บาท/ออเดอร์**

คำนวณจาก:

```text
SUM(amount) / COUNT(DISTINCT order_id)
= 1390 / 6
= 231.67 บาท/ออเดอร์
```

ส่วน:

```text
AVG(amount)
= 1390 / 8
= 173.75 บาท/บรรทัด
```

จึงเป็นค่าเฉลี่ยต่อ **บรรทัดสินค้า (line)** ไม่ใช่ค่าเฉลี่ยต่อออเดอร์

AOV สูงกว่า `avg_line` เพราะบางออเดอร์มีมากกว่า 1 บรรทัดสินค้า

### q11 — ก่อนและหลัง JOIN

| rows_before_join | revenue_before_join | rows_after_join | revenue_after_join |
|---:|---:|---:|---:|
| 8 | 1390 | 8 | 1390 |

`PRAGMA foreign_key_check` คืนค่าว่าง แสดงว่าไม่มี Foreign Key ที่ผิดพลาด

ยอดก่อนและหลัง JOIN เท่ากัน เพราะข้อมูลสมบูรณ์ ไม่มี key ซ้ำในมิติ และไม่มี FK กำพร้า

### ผลกระทบกรณีข้อมูลผิดปกติ

**1. มี key ซ้ำในมิติ**

เช่น `store_key=1` ปรากฏ 2 แถวใน `dim_store`

เมื่อ JOIN จะเกิดการสร้างแถวซ้ำหรือ **fan-out** ทำให้จำนวนแถวและยอดขายหลัง JOIN **สูงเกินจริง**

**2. มี FK ที่ไม่มีข้อมูลอ้างอิง**

เช่น `fact_sales.store_key` มีค่า แต่ไม่มี `store_key` ที่ตรงกันใน `dim_store`

หากใช้ `INNER JOIN` แถวนั้นจะหายไป ทำให้จำนวนแถวและยอดขายหลัง JOIN **ต่ำกว่าความจริง**

### ประเภทของ Measure

| ประเภท | ตัวอย่าง | วิธี Aggregate ที่เหมาะสม |
|---|---|---|
| Additive | `amount` (ยอดขาย) | `SUM` ได้ทุกมิติ เช่น เวลา สินค้า สถานที่ |
| Semi-additive | สต็อกสิ้นวัน (ending stock) | SUM ข้ามสินค้า/สาขาได้ แต่ **ข้ามเวลาไม่ได้** ควรใช้ค่าล่าสุดหรือ AVG ตามบริบท |
| Non-additive | AOV | **ห้ามบวกหรือเฉลี่ยตรง ๆ ข้ามเดือน** ต้องคำนวณใหม่จาก `SUM(amount รวม) / COUNT(DISTINCT order_id รวม)` |

### ข้อค้นพบ


3. AOV เท่ากับ **231.67 บาท/ออเดอร์** สูงกว่า `AVG(amount)` แบบรายบรรทัดที่ **173.75 บาท/บรรทัด**

ความแตกต่างนี้สะท้อนว่าออเดอร์บางรายการมีมากกว่า 1 บรรทัดสินค้า ดังนั้นการเลือกตัวหารจึงมีความสำคัญต่อความหมายของตัวชี้วัด โดย AOV ต้องใช้ `COUNT(DISTINCT order_id)` แทนจำนวนแถว

## ภาพรวมสิ่งที่ได้เรียนรู้

จากแลปนี้สามารถสรุปความแตกต่างของระบบได้ดังนี้:

| หัวข้อ | OLTP | OLAP / Data Warehouse |
|---|---|---|
| จุดประสงค์ | ประมวลผลธุรกรรม | วิเคราะห์ข้อมูล |
| ลักษณะข้อมูล | ข้อมูลปัจจุบัน/รายการ | ข้อมูลสะสมเพื่อวิเคราะห์ |
| การทำงาน | อ่าน-เขียนทีละรายการ | Query และสรุปข้อมูลจำนวนมาก |
| ตัวอย่าง | UPDATE สถานะออเดอร์ | วิเคราะห์ยอดขายรายเดือน |
| Schema | เน้นธุรกรรม | Star Schema / Dimensional Model |
| ตัวอย่าง Operation | INSERT, UPDATE, DELETE | Roll-up, Drill-down, Slice, Dice |
| การสรุปข้อมูล | ไม่ใช่เป้าหมายหลัก | เป็นเป้าหมายหลัก |

**สรุปสุดท้าย:** OLTP เหมาะกับการบันทึกและจัดการธุรกรรมที่เกิดขึ้นในแต่ละรายการ ส่วน OLAP เหมาะกับการนำข้อมูลมาวิเคราะห์ สรุป และเปรียบเทียบในหลายมิติ โดย Star Schema, SQL Aggregation และ Pivot Table เป็นเครื่องมือสำคัญที่ช่วยให้สามารถมองเห็นข้อมูลเชิงธุรกิจได้ง่ายขึ้น
